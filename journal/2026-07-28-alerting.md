# 2026-07-28 — Alerting with Alertmanager and Telegram

**Goal:** stop having to look at a dashboard to know something is wrong.

**Outcome:** Prometheus evaluates alert rules, Alertmanager routes them, notifications arrive
on Telegram.

## Why not just use Grafana alerts

Grafana can alert, but the rules live inside Grafana's database and get configured by
clicking. Prometheus alert rules and Alertmanager config are **plain YAML files** — they can
be reviewed, versioned, and rebuilt from scratch. That is how it is done in production, and
it means the alerting setup is reproducible rather than something that exists only in one
installation's state.

## The split of responsibilities

- **Prometheus** evaluates the rule expressions against its metrics and decides *when* an
  alert is firing.
- **Alertmanager** decides *what to do about it* — grouping, deduplication, silencing,
  and which channel to send it to.

Two jobs, two programs, same pattern as collect/store/display in the monitoring stack.

## Alert rules

`/etc/prometheus/alert.rules.yml`:

| Alert | Expression | For | Severity |
|---|---|---|---|
| `DeviceUnreachable` | `probe_success == 0` | 2m | critical |
| `ExporterDown` | `up == 0` | 2m | critical |
| `DiskSpaceLow` | filesystem free < 15% | 10m | warning |
| `MemoryHigh` | memory used > 90% | 10m | warning |
| `HostRebooted` | uptime < 300s | 0m | info |

The **`for:`** clause is the important part. `for: 2m` means the condition must hold
continuously for two minutes before the alert fires. Without it, a single failed probe — a
dropped packet, a momentary blip — would page you. This is the difference between an alerting
system people trust and one they mute.

Validated before restarting anything:

```bash
promtool check rules /etc/prometheus/alert.rules.yml
promtool check config /etc/prometheus/prometheus.yml
```

`promtool` catches YAML and expression errors up front instead of after a failed restart.

## Wiring Prometheus to Alertmanager

Added to `prometheus.yml`:

```yaml
rule_files:
  - /etc/prometheus/alert.rules.yml

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']
```

## Alertmanager routing

`/etc/prometheus/alertmanager.yml` (token redacted — **this file contains a secret and must
never be committed**):

```yaml
route:
  receiver: telegram
  group_by: ['alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

receivers:
  - name: telegram
    telegram_configs:
      - bot_token: 'REDACTED'
        chat_id: REDACTED
        parse_mode: ''
        send_resolved: true
```

The timing options are what stop alerting from becoming noise:

- **`group_wait: 30s`** — wait briefly after the first alert so related ones arrive in the
  same message rather than as a burst.
- **`group_interval: 5m`** — minimum gap before sending an update about an existing group.
- **`repeat_interval: 4h`** — how often to re-notify about something still broken.
- **`send_resolved: true`** — also notify when it recovers, which matters as much as the
  original alert.

## Debugging the delivery failure

The first test alert reached Alertmanager but never arrived on Telegram. Working the chain in
order rather than guessing:

**1. Did the alert reach Alertmanager?** Queried its API:

```
GET http://192.168.1.12:9093/api/v2/alerts
-> TestAlert, state: active
```

Yes. So submission was fine and the fault was downstream, in delivery.

**2. What did Alertmanager say?**

```bash
journalctl -u prometheus-alertmanager -n 30 --no-pager | grep -i -E "telegram|error|notify"
```

```
msg="Notify attempt failed, will retry later" receiver=telegram
err="telegram: chat not found (400)"
```

**Cause:** Telegram forbids a bot from messaging a user who has not started a conversation
with it first. The bot existed and the token was valid, but nobody had pressed Start.

**Fix:** open the bot and send `/start`. Both queued alerts then delivered.

The lesson is the same one as the 10 Mbps link: the error message named the exact problem.
Reading it beat guessing at config values.

## Telegram bot setup

1. Message **@BotFather** → `/newbot` → returns a token
2. Get the numeric chat ID from **@userinfobot**, or from
   `https://api.telegram.org/bot<TOKEN>/getUpdates` after messaging the bot
3. **Press Start on the bot** — otherwise delivery fails with `chat not found`

In YAML the token needs quotes (it contains a colon, which YAML would otherwise read as a
key/value separator); the numeric chat ID does not.

## Result

Alerts now arrive on a phone when a device stops responding, a disk fills, memory runs high,
or a host reboots — without anyone watching a screen.
